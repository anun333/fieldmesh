## Purpose and scope

Layer zero is the data and device contract every farm app builds on: identity, time, records, observations, devices, messaging and commands. It ships no end-user features. Its job is to make sensor data trustworthy, farmer-owned and portable.

It is for small and mid-size diversified farms, DIY ag builders and researchers, and for developers building apps on their behalf.

In scope:

- A canonical data model for records and sensor observations
- Device, calibration and health tracking
- A message format, link drivers and store-and-forward delivery
- A command contract with acknowledgements and node-side limits
- Local-first storage, export and revocable sharing
- A driver SDK, conformance tests and import/export adapters

Out of scope (built on top): rules and alerts, irrigation logic, dashboards and UI, robots and guidance, ML.

Done means three different apps (an irrigation controller, a livestock water monitor and a research data logger) can each be built without changing layer zero. This is an acceptance test, not a slogan: §15 records what each of the three needs and which clause provides it.

### What v0 actually ships

The full scope above is the contract. The first release implements one vertical slice of it, end to end:

| | In the first release | Deferred |
| --- | --- | --- |
| Links | One (chosen in [open-questions.md](open-questions.md) Q6) | The other four |
| Device drivers | One | The rest of the catalogue |
| Direction | Observations only | **Commands** |
| APIs | SensorThings out | farmOS-compatible in and out |
| Records backend | Native log | farmOS projection |
| Sharing | Export | Grants |

**The substrate is a simulated farm, not hardware.** The contract is built and exercised against a deterministic fictional farm first, because layer zero's hardest clauses are all about failure — reboots, backlog drains, drift, lost acknowledgements — and waiting for a real farm to supply one of each is a multi-year sampling problem. This moves the pilot farm off the development critical path and leaves it on the claims path: §9.2's growing-season requirement is unchanged, and a simulator never satisfies it. See [VIRTUAL_FARM.md](../VIRTUAL_FARM.md).

Commands are deferred on purpose. They carry the liability, they are the hardest part of the contract to change once hardware is in the field, and they benefit most from a season of evidence on the observation path first. Nothing in this spec is weakened by shipping them second; the contract is written now so node firmware can be built against it, and frozen after the first season.

## Design principles

Every rule below traces to a pain point farmers or field deployments report.

| Principle | What it means in layer zero | Pain point it answers |
| --- | --- | --- |
| Auditable | Every reading, command and decision lands in an append-only log | Silent failures, distrust of black boxes |
| Farmer-owned | Local-first, full export in open formats, revocable sharing grants | Fear of losing data ownership, vendor lock-in |
| Honest data | Raw and calibrated values are separate, immutable series; quality is an assertion with provenance, not a mutable column; nothing silently cleaned | Drift, stuck sensors, misleading recommendations |
| Works offline | Store-and-forward delivery; nodes keep local schedules and limits | Poor rural connectivity |
| Modular | Every driver and adapter is optional; removing one breaks nothing | Too many disconnected tools |
| Standards first | farmOS conventions, OGC SensorThings, ISOBUS, Modbus, MQTT, LoRaWAN | Interoperability, the top barrier after cost |
| Safety below software | Hardwired interlocks and fail-safe power-off for anything that moves or pumps | Liability, machinery and water risk |
| Reimplement, don't copy | Build from published specs and documented models | GPL entanglement |

Each principle has an enforcement point, and a principle with no enforcement point is a wish. §16 maps each one to the clause that makes it true.

## 1. Identity

Every entity gets a UUIDv7, generated offline with no coordination.

- **Labels are not keys.** Human names ("north bed") are separate, editable labels. Renaming breaks nothing.
- **IDs do not collide because they are UUIDs.** Every entity also belongs to a site, but the site is for scoping, authorization and sharing — not for uniqueness. Site MUST NOT be part of any key, or renaming or merging a site would break references.
- **UUIDv7 order is ingest order, not measurement order.** Observation IDs are minted by the gateway at ingest, so a reading that spent three days in a node's buffer sorts after readings taken later. Implementations MUST NOT order observations by `id`. Ordering rules are in §2.
- **Radio nodes send short IDs.** A 16-byte UUID in every LoRa packet wastes airtime. Nodes send their native short ID (LoRaWAN DevEUI or Meshtastic node number) plus a channel index; the registry maps that pair to the full point ID.
- **Node message identity is `(site, node, boot, seq)`.** `seq` alone is not enough: a solar node that browns out nightly restarts its counter, and a gateway deduplicating on `(node, seq)` would silently discard every reading after the first reboot. `boot` is a counter the node increments once per cold start and holds in non-volatile memory — a few bytes of EEPROM or flash, and the only non-volatile state a node is required to keep.
- **`seq` is 16-bit, wraps to zero, and resets to zero on each boot.** Wrap is unambiguous because `boot` advances on any power cycle and the gateway tracks the highest `seq` seen per `(node, boot)`; a decrease of more than half the range within one boot is a wrap, not a replay.

Wire identity for a reading is `(node, boot, seq, channel, index)` — see §5. `channel` is one byte, assigned by the device driver and local to the node, so a node can be swapped without reprovisioning a shared index space. A registry-assigned 16-bit point index is an optional extension for nodes with more than 255 points.

## 2. Time

Every observation carries five time fields, so ordering survives outages and bad clocks.

| Field | Type | Meaning |
| --- | --- | --- |
| measured_at | timestamp (UTC) | When the sensor took the reading |
| measured_at_uncertainty | seconds | Half-width of the interval `measured_at` is known to lie in |
| received_at | timestamp (UTC) | When the gateway received it |
| seq | uint16 | The node's sequence number, with `boot` (§1) |
| clock_quality | enum | `gps`, `network`, `rtc_synced`, `rtc_unsynced`, `none` |

- **Nodes with no clock send an age, stamped at transmit time.** The node reports "measured N seconds ago" and the gateway computes `measured_at = received_at − N`. A node draining a store-and-forward buffer MUST recompute the age for each message as it transmits. Stamping the age at sample time and then buffering for three days yields a `measured_at` wrong by the dwell time — the single easiest way to corrupt a dataset silently, and the one a driver is most likely to get wrong.
- **`measured_at_uncertainty` is mandatory and never zero.** It is the honest width of the estimate: sub-second for `gps`, the sync error plus link latency for `network`, the drift budget since last sync for `rtc_unsynced`, and at least the node's sample interval plus transmit latency for `none`. A research logger cannot use a timestamp it cannot bound, and `clock_quality` is a category, not a number.
- **Everything is stored in UTC.** The farm's timezone is a property of the site and is used only for display.
- **Ordering.** Across nodes, order by `measured_at`, and treat two observations whose uncertainty intervals overlap as unordered. Within one node, `(boot, seq)` is authoritative and MUST be preferred over `measured_at`, because a node's own counter is reliable even when its clock is not.
- **SensorThings mapping.** `measured_at` is `phenomenonTime`. The other four have no equivalent and travel in the observation's extension object — `parameters` in SensorThings 1.1, renamed `properties` in the 2.0 draft. See [notes/sensorthings-2.0.md](../notes/sensorthings-2.0.md).

## 3. Core data model

Layer zero has two models joined by shared IDs: records follow farmOS conventions, sensing follows OGC SensorThings, and both write to one log.

A sensor asset and its Thing share one ID, as do a field or bed asset and the feature of interest it represents. Each observation belongs to a datastream, which ties one sensor, one observed property and one unit to its Thing.

Externally, records are served through a farmOS-compatible API and sensor data through a SensorThings-compatible API, so existing tools in both ecosystems work on day one.

### 3.1 Datastreams

A datastream ties one sensor, one observed property and one unit to its Thing. The SensorThings 2.0 draft permits several observed properties per datastream; one property per datastream is a subset of that, so this model maps unchanged to 1.1 and to 2.0.

**Sampling and latency are different numbers, and the second one spends the battery.** A soil-moisture series sampled hourly and a trough float sampled every five minutes can share a node, but what the radio costs is set by how quickly each series must *arrive*, not by how often it is read. Reading a sensor is a rounding error — measured at under 2% of a node's consumption in every realistic configuration — while one transmit at the slowest data rate costs more than a day of sampling. A series that is merely informative declares a loose `max_latency` and rides along in whatever message is next; a series someone will act on declares a tight one and pays for it.

**Feature lives on the datastream, not on each observation.** For a fixed installed sensor the observed feature never changes, so repeating its UUID on every row wastes storage and airtime for no information. An observation MAY carry its own feature, and does so only when it genuinely varies: a handheld meter, a sample, a sensor on a moving thing.

| Field | Type | Notes |
| --- | --- | --- |
| id | UUIDv7 | |
| thing, sensor, observed_property | UUIDv7 | |
| unit | UCUM code | Declared once here; see §3.4 |
| feature | UUIDv7 | The field, bed, tank or animal this series observes |
| kind | enum | `raw` or `derived` |
| derived_from | UUIDv7 | The raw datastream this one is computed from; null when `kind = raw` |
| expected_interval | seconds | How often this series is sampled. Drives staleness (§4.2) |
| max_latency | seconds | How stale a reading of this series may be when it reaches the gateway. Drives the node's transmit schedule, and therefore its battery (§5.2) |
| thresholds | object | Health-check thresholds; see §4.2 |
| buffer_policy | object | Node backlog behaviour; see §5.3 |

### 3.2 Observations are immutable, and calibration is a separate series

An observation is written once and never altered. There is no mutable field on it — not the result, not the quality flag. Two consequences, and they are the heart of *Honest data*:

**Raw and calibrated values are separate datastreams.**

- The **raw datastream** holds exactly what the node sent. It is never superseded, never recalculated, and is the archival truth. If everything else is lost or wrong, this is what a farmer still owns.
- The **calibrated datastream** is derived from it, one per raw datastream, carrying `derived_from` and, on each observation, the calibration record that produced that value.

A client that wants raw values reads one datastream; a client that wants usable values reads the other. Both are ordinary SensorThings Datastreams, so this is honest *and* standard, rather than honest by convention.

**Recalibration appends; it never rewrites and never duplicates a timestamp.**

A new calibration produces new observations in the calibrated datastream, each carrying `supersedes` pointing at the row it replaces. The superseded row stays in the log forever. Exactly one **live** observation exists per `(datastream, measured_at)`, where live means nothing supersedes it.

This is the clause that makes the SensorThings promise survive the first recalibration. Keeping two results in one series — the v0 design — would have put two observations at the same `phenomenonTime` in one Datastream, so every existing client would double its data points or show a discontinuity, which is exactly the "works on day one" claim failing on the most ordinary maintenance event there is.

| Field | Type | Notes |
| --- | --- | --- |
| id | UUIDv7 | Minted at ingest. Not a sort key (§1) |
| datastream | UUIDv7 | |
| feature | UUIDv7 | Optional override; null means the datastream's feature |
| measured_at, measured_at_uncertainty, received_at, seq, clock_quality | see §2 | `boot` travels with `seq` |
| result | number or string | Raw as sent in a `raw` datastream; calibrated in a `derived` one |
| calibration | UUIDv7 | The calibration applied; null in a `raw` datastream |
| supersedes | UUIDv7 | The observation this replaces; null if none |
| provenance | object | Firmware version, driver and version, gateway and version |

- **Calibration is selected by `measured_at`, never by ingest time.** The gateway MUST apply the calibration that was in force when the reading was taken. Applying whatever is current at ingest would silently give wrong coefficients to every reading that arrived late from a buffer — a violation of *Honest data* produced entirely by an unstated default.
- **Derivation is reproducible.** `(raw value, calibration record, driver version)` MUST be sufficient to recompute a derived result exactly.
- **A calibration MAY declare an output resolution.** `0.001 x 86` is exactly `0.08600000000000001` in IEEE 754 — correct, reproducible, and a claim of seventeen significant figures that no probe can support. Rounding to a declared resolution is not cleaning the data; it is declining to assert precision the instrument does not have. Because the resolution is part of the calibration record, the derivation stays reproducible, and a client is not handed false precision to display. A derivation that depends on anything else — ambient state, wall-clock time, another series — MUST be recorded in `provenance`.

### 3.3 Quality is an assertion with provenance

Quality is not a column on the observation. It is its own append-only record, because a quality judgement is a claim made by a particular check, under a particular threshold, at a particular time — and all three change.

| Field | Type | Notes |
| --- | --- | --- |
| id | UUIDv7 | |
| observation | UUIDv7 | What is being judged |
| flags | set of enum | `suspect`, `stuck`, `out_of_range`, `rate_exceeded`; empty set means no objection |
| usable | enum | `good`, `questionable`, `bad` — the one-value summary |
| check, check_version | string | Which check produced this |
| threshold_version | UUIDv7 | The threshold record in force |
| asserted_at | timestamp | |
| assertor | enum + UUIDv7 | `foundation` or `person`, and which |
| supersedes | UUIDv7 | The assertion this replaces |
| evidence | object | Which individual checks ran, which fired, and why (added by amendment; see §17) |

Why this shape:

- **A single enum cannot express reality.** A sensor can be stuck *and* out of range at once. `flags` is a set; `usable` is the one value an app that does not care about detail can read. Two conforming implementations now agree on the same input, which a single enum did not guarantee — fatal for a suite meant to certify conformance.
- **Changing a threshold does not rewrite history.** Every assertion names the threshold version it used. Retuning a threshold produces new assertions that supersede the old ones, and the old ones remain visible, so a false alarm can be traced to the threshold that caused it and the fix can be audited.
- **A person's override is a new assertion, not an edit.** `assertor = person` with a higher precedence than `foundation`. The original machine assertion stays.
- **Staleness is not here.** See §4.2.
- **Device warnings are not here.** Battery and signal are properties of a device, not of a reading; see §4.3.

**One assertion per assessment run.** `check` names an *assessment*, not a single check, and `flags` carries the union of everything that fired in it. §4.2 lists four checks that each produce one flag, and the precedence rule below selects exactly one live assertion — so if each check wrote its own assertion, two firing together would mean one wins and the other's flag silently disappears. That is the loss this model exists to prevent, so the foundation runs the suite, unions the flags, and records per-check detail in `evidence`. A person's override is still a separate assertion, which is what precedence is for.

**Precedence, so implementations agree:** the live assertion for an observation is the non-superseded one with the highest precedence, where `person` outranks `foundation`; ties break by `asserted_at`, then by `id`. `usable` is derived as `bad` if `stuck` or `out_of_range` is set, `questionable` if only `suspect` or `rate_exceeded` is set, `good` if `flags` is empty — unless a person asserts otherwise.

**SensorThings mapping.** 1.1 carries `resultQuality` on Observation, typed `DQ_Element` with multiplicity zero-to-many, which fits this model natively. The 2.0 draft has **no `resultQuality` attribute at all** — Table 17 lists only `id`, `phenomenonTime`, `result`, `resultTime`, `validTime` and `properties`. Under 2.0 the live assertion travels in `properties`. This is worth raising with OGC while 2.0 is unpublished; see [notes/sensorthings-2.0.md](../notes/sensorthings-2.0.md).

### 3.4 Units and observed properties

- Units use UCUM codes, declared once on the datastream. SensorThings 1.1 already says `unitOfMeasurement` values SHOULD follow UCUM, and the 2.0 draft moves the unit inside a SWE-Common `resultType`, which also carries UCUM codes — so this is the standards-aligned choice in both versions rather than a preference.
- Observed properties reference a shared vocabulary by URI, never free text. Vocabulary choice is open; see [open-questions.md](open-questions.md) Q4.
- A datastream with no meaningful unit (a boolean, a state) sets the unit to null rather than inventing one.

## 4. Devices, calibration and health

Sensors are maintained assets with their own history, because drift and hardware failure are the most common reasons field data goes wrong.

### 4.1 Device record

Each device record holds:

- Install location, depth and orientation, with dates
- Firmware version, also stamped into each reading's `provenance`
- Calibration history: method, reference used, coefficients, date, who did it, and the interval it is in force for
- Last seen, and the current `boot` counter
- A maintenance log: cleaned, moved, replaced, recalibrated
- Declared capabilities from the driver manifest (§8): dedup persistence, delivery confirmation, safe states

A calibration record carries a validity interval, because §3.2 selects calibration by `measured_at` and that requires knowing what was in force when.

### 4.2 Health checks produce quality assertions

Checks run in the foundation and write assertions (§3.3), never mutations:

| Check | Flags | Example |
| --- | --- | --- |
| Flatline | `stuck` | Identical values for longer than physically plausible |
| Range | `out_of_range` | Soil moisture above saturation |
| Rate of change | `rate_exceeded` | A jump no real process could produce |
| Cross-check | `suspect` | Disagreement with a redundant sensor on the same feature |

**A feature with one sensor has no drift detection, and drift is the commonest real failure.** Measured on the virtual farm, scoring each fault against ground truth: a single probe catches a disconnected sensor (100% recall) and a frozen one (87%), and catches **drift, bias and intermittent noise not at all — 0% recall on all three**. Every reading is individually plausible and the series looks healthy, so no check that looks at one series has anything to go on. Adding a second probe on the same feature takes those to 79%, 100% and 19%, entirely through cross-check. So redundancy is not a refinement: on a series anyone will act on, it is the difference between seeing three fault modes and seeing none, and that belongs in an installation decision rather than a wish list.

**Cross-check says `suspect` and never worse.** When two probes disagree it cannot say which is wrong, so calling either one bad would be a guess dressed as a measurement. A farmer deciding which probe to pull needs that distinction.

**Flatline latency depends on when the fault begins, not only on the threshold.** Part of an identical run can precede the fault, because a healthy probe already repeats overnight when evapotranspiration is near zero. A probe that freezes at dawn is caught sooner than one that freezes at midday, through no merit of the detector — so a latency figure needs the onset time beside it to mean anything.

**Flatline MUST NOT be applied to a regulated quantity.** A float-controlled trough level, a thermostat-held temperature, a pressure held by a regulator — these are constant *by design*, and constant is the healthy state. Measured on the virtual farm: a working float holds a trough at one reported value for 226 consecutive samples, nearly nineteen hours. Flatline on such a series is a category error that reports a fault every day. The check that catches a stuck float is **range**.

**A flatline threshold MUST exceed the quantisation dwell.** A sensor reports in steps, and when the true value moves more slowly than one step the readings are *identical and correct*. Measured: a soil probe reporting three decimals, sampled every fifteen minutes, repeats a value for up to eight hours overnight when evapotranspiration is near zero. A six-hour threshold therefore fires nightly on a healthy probe. The floor for `flat_seconds` is how long the true process takes to move by more than one reported step, which is a property of the sensor's resolution and the process's rate — not a number to pick by feel.

**A threshold lives on the datastream whose values it bounds.** `max: 0.55` is soil moisture, so it belongs on the *derived* series; a limit on the integer a probe reports belongs on the raw one. They are different numbers in different units and putting one on the wrong series makes it silently inert — the check runs, finds nothing to compare against, and reports no objection.

**Thresholds are expressed in physical units, not in samples.** "Identical values for longer than physically plausible" is a duration, and how long a frozen reading is implausible is a property of the measurand rather than of how often a node samples. A count-based threshold means different things on two farms: twelve samples is twelve hours at hourly sampling and one hour at five-minute, so the "same" threshold catches a fault on one farm and misses it on the other. Flatline therefore takes `flat_seconds`, with a sample count kept only as a confidence guard — two equal readings an hour apart prove little however long the span between them.

These four contribute to **one** assertion per run, not one each (§3.3). Cross-check flags only `suspect`, never worse: when two probes disagree it cannot say which is wrong, and calling either one bad would be a guess dressed as a measurement.

Thresholds live on the datastream with sensible defaults, so apps can tune them without code. Every threshold is a versioned record, and every assertion names the version it used (§3.3). Defaults are deliberately loose — a default that fires often costs the farmer's trust in every flag, which is more expensive than a missed detection.

**Staleness is a datastream state, not a reading flag.** "No reading for 3× `expected_interval`" is a statement about a series at a moment in time, not about any particular observation. Flagging the last good reading as `stale` would mean reaching back and mutating a record that was correct when written, because a *later* reading failed to arrive — an append-only violation that also destroys the meaning of the value. Staleness is exposed as current datastream health, and the absence itself is already recorded honestly as a gap (§5.4).

### 4.3 Device health is observations, not side-channel state

Battery voltage, RSSI and SNR are measurements of the device, so they are datastreams on it like any other. Trends, thresholds, quality assertions, export and audit then work on them for free, instead of needing a parallel mechanism. The SensorThings 2.0 draft explicitly blesses this case: an observation whose target is a sub-part of the Thing itself, battery level being its own example.

A low-battery warning is therefore a threshold on a device datastream, surfacing as device health — not as a flag on an unrelated soil-moisture reading, which is what a `device warning` value in a reading-level quality enum would have meant.

### 4.4 Resources

Pumps, wells and power sources are resource assets with declared capacities (flow, pressure, watts). Bookings against them are enforced in layer zero's command path (§6.5), not only by the layer-1 scheduler. Tasks for people are pending logs, following farmOS, rather than a separate entity.

## 5. Messaging and link layer

One compact message format rides over any link; the gateway expands it into full observations.

### 5.1 A reading's path

1. The node samples, applies nothing, and packs a compact binary message.
2. The node buffers it until delivery is confirmed by whatever means its link offers (§5.2).
3. A link driver carries it: Meshtastic, LoRaWAN via ChirpStack, wifi, cellular or wired.
4. The gateway resolves IDs through the registry, computes times (§2), drops duplicates on `(site, node, boot, seq)`, writes the raw observation, then derives the calibrated one (§3.2) and runs health checks (§4.2).
5. Raw and derived observations are written to the append-only log and the time-series store, then published on the bus (MQTT for edge devices; bridged to ROS 2 for robots and machinery).

### 5.2 Messages and batching

A message carries a format version, `(node, boot, seq)`, and one *or more* readings. Batching is not an optimisation to add later: one reading per message cannot fit a useful sample rate inside a 1% duty cycle, and retrofitting it would change the dedup contract and the wire format.

```
message  := version, node_short_id, boot, seq, base_age, dropped, reading+
reading  := channel, age_delta, value
```

`dropped` is the count of readings this node evicted from its buffer since its last
message, which §5.3 requires it to report so a loss is recorded as a gap rather than
as readings that quietly never existed.

**Ages are whole seconds, and that bounds the sample interval.** Two readings on one
channel that compute the same `measured_at` would be two live observations at one
instant, which §3.2 forbids and which breaks every SensorThings client. So a node
MUST NOT sample one channel faster than the age field can distinguish: a driver
declaring a sub-second interval is a configuration error, not a runtime condition.
A gateway that receives such a collision anyway records it and keeps the first
reading, because writing both would violate the invariant and discarding silently
would lose a reading without saying so.

A reading's identity is `(node, boot, seq, index)` where `index` is its position in the message. The dedup key stays `(site, node, boot, seq)` — one key per message, not per reading — so deduplication, gap detection and batching do not interfere.

`base_age` is stamped at transmit time (§2); each reading's `age_delta` is relative to it.

- Link drivers are interchangeable and share one interface: send, receive, link health, **and a declared delivery-confirmation capability**: `confirmed`, `gateway_receipt` or `none`.
- "Buffer until the link confirms delivery" is not available on the primary target links. Meshtastic and unconfirmed LoRaWAN uplinks return no receipt, and confirmed LoRaWAN uplinks spend a downlink per message, which exhausts the downlink budget and the battery. For a `none` link, the gateway periodically sends a cumulative acknowledgement — the highest contiguous `seq` it holds for that `(node, boot)` — and the node releases its buffer up to that point. One small downlink retires many uplinks.
- Messages must fit the smallest link's payload. In the EU 868 MHz bands a 1% duty-cycle sub-band allows about 36 seconds of transmit time per hour, per sub-band, per device; EU868 also defines 0.1% and 10% sub-bands, and LoRaWAN deployments add a network fair-use policy on top. Treat 36 s/hour as the common case, not as the limit, and take the real budget from the link driver.
- Encoding: **CBOR packed arrays with a CDDL schema**, versioned with the spec and carrying its version in every packet. Decided on measurement; see [notes/q5-encoding-measurement.md](../notes/q5-encoding-measurement.md). A hand-packed layout is documented as an escape hatch for a node draining a very long backlog at the slowest data rate, distinguished by the version byte.
- `node_short_id` is **optional on the wire**, present per link driver. On LoRaWAN the session already identifies the device, so the bytes are waste; on Meshtastic they are required. Measured at four bytes a message, which is a reading every other message at DR0.
- **Batch size is computed from the current data rate, never fixed at build time.** Sizing a batch to exactly the payload limit is a trap: LoRaWAN MAC commands piggyback in `FOpts` and shrink the available `FRMPayload`, and ADR moves the data rate under a running node. The encoder takes a maximum-payload argument and packs what fits, with headroom.
- **A resend MUST reuse its sequence number.** This is the same rule §6.3 states for commands, and it holds here for the same reason: the dedup key is `(site, node, boot, seq)`, so a retry under a fresh number is a *new message* to the gateway. It then writes the same readings again at timestamps that differ by the rounding of a recomputed age — phantom readings a second away from the real ones, in a series nobody can later untangle. Measured on a 6%-loss link: 2498 observations where 768 were expected.
- **An acknowledgement deadline is mandatory wherever cumulative acknowledgement is used.** A node MUST give up waiting and resend after a stated interval. Without one, a single lost frame stalls the gateway's highest contiguous sequence at the hole below it permanently, and the node holds every later reading until it begins evicting — a node that looks healthy and delivers nothing.
- **A node has one clock and MUST use it at both ends of an age.** The cancellation that makes §2 work depends on it: subtracting two readings of the same wrong clock removes the error exactly, so a node six hours wrong still reports correct times. Taking the sample time from one source and the transmit time from another destroys the property silently, and nothing downstream can detect it.

### 5.3 Backlog policy

A node with a five-minute interval accumulates about 288 readings a day. After a three-day outage it holds ~900 readings and can spend 36 seconds an hour transmitting. What it discards, and in what order, is a contract decision, because the target apps want opposite answers: a livestock water monitor needs the newest reading first, a research logger needs the series unbroken.

`buffer_policy` on the datastream declares:

| Field | Meaning |
| --- | --- |
| buffer_max | Readings the node retains before evicting |
| eviction | `oldest` or `newest` — which is dropped when full |
| drain_order | `fresh_first` or `chronological` |
| downsample_on_backlog | Optional: aggregate buffered readings rather than drop them |

A node that evicts MUST report the count, so the loss is recorded as a gap rather than disappearing.

### 5.3.1 The transmit schedule, and where a sensor is installed

**A node's transmit interval is the tightest `max_latency` among the series it carries.** A trough float that must be known within five minutes forces the radio awake every five minutes however sleepy everything else on that node is, so latency is not a per-series cost — it is imposed on every series sharing the radio.

Two consequences, both measured ([notes/power-budget.md](../notes/power-budget.md)):

- **Slowing a sensor down to spare the sensor saves nothing.** Sampling is under 2% of a node's energy. What a higher sample rate costs is the airtime to *send* what it produced: twelve readings an hour instead of one nearly triples a node's consumption, and almost none of that is the probe.
- **Which node a sensor sits on is the power decision, and it outweighs every configuration choice.** The same hourly soil probe lasts around 1500 days on its own node and around 130 days on a node a five-minute trough float keeps awake. Nothing in the sample-rate or encoding space comes within an order of magnitude of that.

**A latency requirement is a ceiling, not a schedule.** `max_latency` is the longest a reading may wait, not how often the radio should speak. A node sampling twelve readings an hour and sending one message an hour that holds five is permanently behind and will lose data forever while appearing healthy — inside its latency ceiling the whole time. So a node MUST also drain whenever it holds more than one frame's worth and its duty cycle affords the airtime.

**An infeasible configuration MUST be refused at registration.** Compare what a node produces — the sum of `3600 / sample_interval` across its channels — against what it can deliver, which is the readings that fit one frame at the current data rate multiplied by the frames the duty budget affords. If production exceeds delivery, no buffer policy saves it: the node will lose data permanently, and the farmer will discover it as unexplained gaps in month three. The foundation says so when the device is registered, with the three things that fix it: sample less often, raise the data rate, or split the channels across nodes.

So the installation rule: **do not co-locate a series with a loose latency on a node whose tightest latency is short**, unless the wiring makes it unavoidable. An extra reading that fits a message the node was already sending is close to free; an extra *transmission* is not. A driver manifest declares both intervals per point (§9.1) so the foundation can tell a farmer which of their nodes is short-lived and why.

### 5.4 Gaps

Gaps in `(boot, seq)` are logged as gaps and never filled with guesses. A `boot` increment is a reboot, not a gap, and is logged as such. Modules watch for new observations and events through a stable subscription API (§7.5); nothing above layer zero polls.

## 6. Command contract

Commands state a desired outcome, carry their own safety bounds, and are safe to send twice, so a lost or repeated message can never leave a pump or valve in a bad state.

### 6.1 What a command carries

- A UUIDv7 command ID, held server-side
- A short command sequence, node-scoped, which is what actually travels on a constrained link (§6.2)
- The target point and the desired state, not a toggle: "valve 3 open", never "flip valve 3"
- A maximum duration or expiry, after which the node reverts to its safe state on its own
- Who issued it and why — a user, a regimen, a rule — for the log
- An optional `dry_run` flag

### 6.2 Identity on constrained links

A 16-byte UUID does not belong in a downlink. §1 bans it for uplinks on airtime grounds and the same arithmetic is worse downward: LoRaWAN Class A offers two short receive windows after an uplink, and DR0 gives about 51 bytes of payload for the whole command.

So the UUIDv7 stays server-side, and the wire carries a short command sequence scoped to `(node, session)` — the same registry-mapping pattern already used for point IDs. Issuer and reason are stamped by the gateway and never transmitted. The registry mapping is part of the audit chain: "which command did the node actually run" resolves through it, so the mapping is itself logged.

### 6.3 Idempotency has a stated bound

"Repeats with the same ID are ignored" is only true while the node remembers the ID, and a node's memory is small and clears on power loss. Unbounded, the claim fails in exactly the case the contract exists to prevent: a retry across a brownout runs the pump twice.

- A node MUST ignore a repeated command sequence until that command's expiry has passed, plus a margin declared in its driver manifest.
- A node MUST either persist that set across cold starts, or declare `dedup_volatile` in its manifest. For a `dedup_volatile` node, the foundation MUST refuse to issue any command whose double execution is not bounded by a node-side maximum runtime — the remaining protection being the max-runtime limit and the safe state on power loss, which is then stated rather than assumed.
- **A retry MUST reuse the same command ID and sequence.** Minting a new ID for a retry is a conformance violation, because it defeats every deduplication guarantee above.

### 6.4 Acknowledgement, and the honest absence of one

The node answers `accepted`, `rejected` with a reason, or `completed`.

**No acknowledgement within the link timeout means `unknown`, not "not delivered."** A command lost on the way out and an acknowledgement lost on the way back are indistinguishable from the server, and the node may well have acted. Recording that state as "not delivered" invites a reissue as a fresh command, which double-executes. The contract is: the state is `unknown`, the resolution is a retry with the same ID (§6.3), and the backstop is the node's own expiry and maximum runtime.

A `dry_run` acknowledgement MUST name the limit that would have been hit, if any. A bare rejection teaches a backtest nothing.

### 6.5 Limits and shared resources

Node-side limits are configured on the node, not sent with each command: maximum runtime, minimum off-time, interlocks with other outputs, and the safe state on power loss or link loss. The server cannot override them.

**Shared-resource capacity is checked in layer zero, beside per-point authorization.** v0 put the resource registry in layer zero but the booking in the layer-1 scheduler, while also declaring layer 1 non-safety-critical and expected to be down sometimes — so "two modules can never overdraw one well" rested on a component designated optional, and per-node interlocks cannot see another node's valve. Capacity is the same kind of check as permission, on a path that already exists, so it belongs here. The layer-1 scheduler still books ahead; layer zero refuses a command that would exceed a declared capacity regardless of who issued it.

Hardwired interlocks for machinery and high-energy loads sit below all of this and are outside software's reach.

### 6.6 Standards alignment

Tasking has never been part of SensorThings Part 1, in either version — it lives in a separate document, *Part 2: Tasking Core* (OGC 17-079r1). So the 1.1-versus-2.0 choice in §10 does not bear on this one. The choice here is Part 2 Tasking Core as it stands, or OGC API — Connected Systems Part 2, whose ControlStreams are published and purpose-built for commands flowing to and from systems. Open; see [open-questions.md](open-questions.md) Q3b.

## 7. Storage, ownership and sharing

The farm's own machine holds the authoritative copy; the cloud is optional and never required to operate.

### 7.1 The log is authoritative

Every change to records, every observation, every command and every decision is an event. Current state is derived from the log, so history can always be replayed and audited.

**farmOS is a projection of the log, not the backend.** v0 listed farmOS as the records backend and as an adapter at once, which cannot hold: if a mutable Drupal database owns records, then the authoritative copy is not the log, state is not derived from the log, removing an "adapter" destroys the records, and there are two sources of truth with no reconciliation. Instead:

- Writes append to the log, always.
- A projector materializes farmOS one-way, so existing farmOS clients keep working.
- Writes arriving through the farmOS-compatible API are translated into appended events, not applied to Drupal directly.

Every principle survives this; the alternative split is recorded in [open-questions.md](open-questions.md) Q8.

### 7.2 Two stores

High-frequency sensor data goes to a time-series store with downsampling and retention rules. Records — assets, logs, plans — go to the main store. Years of readings never slow everyday records. Both are projections of the log; neither is authoritative.

### 7.3 Corrections and erasure

- **A correction is a compensating event.** Nothing is ever updated in place. The farmOS-conventions side of the model is CRUD-shaped and will tempt an implementer to mutate a row; the conformance suite tests that they did not.
- **Erasure, when it is genuinely required** — a worker's personal data, for instance — is performed by destroying the payload's encryption key and retaining the event skeleton, so the log stays continuous and auditable while the content becomes unrecoverable. An append-only log with no erasure story is a liability the first time someone has a legal right to removal.

### 7.4 Offline edits

Devices that edit while disconnected sync later. Conflict resolution happens at projection time, deterministically, and never by discarding an event.

**Ordering uses hybrid logical clocks, not wall clocks.** Last-writer-wins on wall-clock time is unsafe in this system by its own admission: §2 records `clock_quality` precisely because farm devices' clocks cannot be trusted, and a node reporting `clock_quality = none` must never win a last-writer contest against a GPS-synced one on the strength of a bad timestamp. Every event carries an HLC stamp; LWW-per-field applies to HLC order.

Where two writers touched the same field concurrently and the field is one where that matters, both versions are retained and a conflict event is emitted for a person to resolve. The conflict event is itself in the log.

### 7.5 Subscriptions

"Nothing above layer zero polls" implies delivery guarantees, so they are stated: at-least-once, with a durable cursor each subscriber can replay from. A module that restarts, silently misses the events it was down for, and cannot replay them will make wrong decisions while its decision events claim full provenance.

### 7.6 Export and sharing

- **Full export.** Everything exports in open formats (CSV, JSON, GeoJSON for geometry) at any time, with no fee and no support ticket. Raw and calibrated series, quality assertions and their threshold versions are all included; an export that carried only calibrated values would be the silent cleaning this spec exists to prevent.
- **Revocable sharing.** A grant states what data, to whom, for what purpose and until when. A grant MUST also state whether it covers observations that arrive *after* the grant was made, and whether the grantee may re-share. Both matter immediately for research and co-op use, and leaving them unstated means two implementations will behave differently on the farmer's most sensitive operation.
- **Revocation stops future access and does not retract what was already delivered.** Say this plainly to the farmer at the moment they grant, because "revocable" reads as "I can take it back".

### 7.7 Decisions and required records

Automated actions are logged as decision events: the observations used as inputs, the rule or model and its version, the output, and the trust level it ran under. Any action can be traced back to why it happened.

The log model must be able to produce certification and compliance records — organic, produce-safety water testing, pesticide application — without custom code. Exact requirements vary by country and program. Note that compliance records depend on quality assertions, which depend on thresholds: anyone who can edit a threshold can change what a compliance report says, which is why threshold edits are privileged and logged (§8.2).

## 8. Security

Secure by default, because no farm will harden its network later.

### 8.1 Devices and links

- **Device onboarding.** Each device gets its own key when it is registered. Unregistered devices are heard but not trusted, and their data is quarantined until someone approves them.
- **Signed firmware.** Updates are signed and the version recorded. LoRa links are too slow for over-the-air updates, so the spec plans for physical update visits on those nodes.
- **Encrypted links where the link allows it.** LoRaWAN and Meshtastic both offer link encryption; wired and wifi links use TLS to the gateway.
- No default passwords, no open admin ports, and the log records every login and permission change.

### 8.2 Users, roles and privileged operations

Roles: owner, manager, worker, viewer, service account. Commands are authorized per role and per point. Three operations are privileged beyond ordinary writes and were unassigned in v0:

| Operation | Minimum role | Why |
| --- | --- | --- |
| Issue or revoke a sharing grant | owner | It moves the farm's data off the farm |
| Edit a datastream threshold | manager | It changes quality assertions, which change compliance records (§7.7) |
| Override a quality assertion | manager | Same, for one reading |

Node-side limits are not in this table because no role can change them remotely; they are configured on the node (§6.5).

### 8.3 Modules

Modules are permissioned like users. Each declares what it may read, write and command, scoped per point; the farmer grants it at install and the foundation enforces it, which is what makes third-party modules safe to run. Packaging and isolation are open; see [open-questions.md](open-questions.md) Q11.

## 9. Driver SDK and conformance tests

Anyone can add hardware without touching the core, and a passing conformance suite is what makes a driver or implementation official.

Two driver kinds, one plugin interface each:

- **Device drivers** turn a protocol into raw readings and accept commands: Modbus RTU/TCP, SDI-12, I2C, 1-Wire, 4–20 mA and 0–10 V analog, BLE, local HTTP APIs, CAN/J1939/ISOBUS, NMEA and NTRIP.
- **Link drivers** move messages: Meshtastic, LoRaWAN via ChirpStack, MQTT, wifi, cellular, wired.

### 9.1 Driver manifest

A driver declares, and the foundation handles the rest:

| Declaration | Used by |
| --- | --- |
| Points, with channel indices | §1 wire identity |
| Units (UCUM) and observed-property URIs | §3.4 |
| Sample interval, and maximum latency, per point | §3.1, §4.2 staleness, §5.3.1 transmit schedule |
| Safe states | §6.5 |
| Clock source, and timestamp uncertainty budget | §2 |
| Delivery-confirmation capability | §5.2 |
| Backlog policy defaults | §5.3 |
| Dedup persistence, or `dedup_volatile` | §6.3 |

Python is the first SDK language, with Rust for the edge daemon.

### 9.2 Conformance suite

- Simulated devices for every driver kind — these are not fixtures written per test but the devices of one canonical deterministic farm, which the suite also uses as a completeness gate: a clause of this spec that nothing on that farm exercises is a clause nothing tests. See [VIRTUAL_FARM.md](../VIRTUAL_FARM.md)
- Replay of real recorded field data
- **Scored detection, not asserted detection.** A health check's claim to catch drift or a stuck probe is measured against ground truth — precision, recall, false-alarm rate on clean rows, detection latency from onset, and whether each fault episode was caught at all. "It flags the obvious case" is not a measurement. The scorer must not be able to see what was injected; a detector scored against the fixture that produced it is scored against itself
- **A control drill, every time.** A run with nothing wrong must flag nothing. This is not a formality: the first scored run on a clean farm reported a 99.8% false-alarm rate, because the cross-check was comparing a derived series in physical units against a neighbour's raw series in wire units — 0.280 against 280. No amount of fault-detection recall would have revealed that
- Fault injection: drift, stuck values, dead batteries, dropped and repeated messages, clock jumps, **node reboots with counter resets, and buffer drains after multi-day outages**
- Command safety tests: lost acks, duplicates, link loss mid-command, **retry across a node reboot**
- Append-only tests: that a correction appended rather than mutated, that recalibration superseded rather than overwrote, that a threshold change did not alter historical assertions

Reliability claims require at least one full growing season of field data, not a few weeks in the lab.

**The suite cannot certify anything until the blocking open questions are closed.** A conformance test needs a decided wire format, a decided unit system and a decided point-index scheme. "A passing suite is what makes an implementation official" is a claim the suite cannot yet support; [open-questions.md](open-questions.md) marks which questions block.

Ship on 1.1: the 2.0 draft is unpublished, and its serialization differences are confined to one layer if the adapter is written with that in mind.

**Both versions are served side by side once 2.0 is published**, from one internal model, at separate base paths. This is the ecosystem's expected pattern rather than an accommodation: FROST-Server, the most widely deployed implementation, ships 1.1 and 2.0 API plugins that can be enabled simultaneously over a single data model. The internal model is deliberately richer than either serialization, so neither version's Observation shape may leak into it — that constraint is what keeps the migration a day's work. Validate both serializations against FROST-Server from the first release, since in practice it is what defines conformance in the field.

## 11. Layers above

Everything above layer zero is optional and depends only on the layers below it.

| Layer | What lives there | Must get right |
| --- | --- | --- |
| 1. Core services | Rules and alerts, scheduler for sequences and regimens, notifications, query and analytics | Rules backtested on past seasons before going live; resource conflicts resolved; alerts escalate and need acknowledgement |
| 2. Domain modules | Irrigation, greenhouse climate, livestock, storage and cold chain, field operations, robotics, inputs and inventory, harvest and traceability, compliance reports | Built only on layers 0 and 1; each one removable |
| 3. Decision support | Agronomic models, forecasting and ML, cost per field or crop, simulation | Models versioned and calibrated per site; confidence shown; readings whose live assertion is not `good` excluded, with the exclusion recorded |
| 4. Apps and interfaces | Phone field app, desktop planning, SMS and voice, a plain-language assistant | Offline, glove- and sunlight-friendly, bilingual; the assistant cites readings and never commands without approval |
| 5. Ecosystem | Module registry, multi-farm and co-op use, research sharing, buyer and certification exports | Signed modules with declared permissions; sharing only by consent |

Rules for building upward:

- **Dependencies point down only.** A module never reaches into another module, only into the layers below, so any module can be removed.
- **Trust ramp per module.** Every automation runs as advisory, approval or autonomous. Farms move up one step at a time, and the level is recorded on every decision event.
- **Nothing above layer zero is safety-critical.** If layers 1 to 4 go down, nodes keep running their local schedules and limits, and layer zero still refuses commands that exceed a declared capacity or a per-point permission.
- **Shared limits are enforced, not hoped for** — in layer zero (§6.5), not only in the layer-1 scheduler.
- **Cost visibility early.** Showing cost and return per field answers the barrier farmers name most often: unclear value.

## 12. Versioning and governance

The spec is published separately from the code, so others can build on it or write their own implementation.

- **Semantic versions.** Breaking changes only in major versions, each with a written migration. The message format carries its version in every packet.
- **Spec, reference implementation, conformance suite** are three versioned artifacts released together.
- **Change process.** Public proposals with a comment period before a breaking change lands.
- **License, liability, sustainability, legal entity.** Open; [open-questions.md](open-questions.md) Q2 and Q9.
- **Partners.** University extension services already have farmer trust and run research plots, which makes them natural pilot partners.
